The budget gate in front of your model providers.

An OpenAI-compatible gateway that reserves each request's worst-case cost in SQLite before forwarding, settles at the provider-reported usage, and refuses the request that would cross the line.

Run it locally How the gate works

No account, no SDK, no spend: the default config runs on deterministic fake providers.

One request, four commitments

The gate is the only path to a provider.

Every chat completion passes the same sequence. A request that cannot reserve its worst-case cost never leaves the process.

  1. 01 — AUTHENTICATE

    Resolve the tenant

    A bearer key maps to one project: its allowlist, rate limit, concurrency cap, and budget policy.

  2. 02 — RESERVE

    Check the worst case

    Input tokens plus max_tokens priced at the route's rates, then checked against the per-request, daily, and monthly limits inside one BEGIN IMMEDIATE transaction.

  3. 03 — ROUTE

    Forward once, fall back carefully

    Ordered targets are tried only for idempotent requests whose failure is classified transient. A permanent 4xx stops at the first attempt.

  4. 04 — SETTLE

    Replace the estimate with the bill

    The reservation settles at reported usage, or at zero when the provider failed. Every attempt keeps its tokens, latency, cost, and outcome.

What you get

Spend control with receipts.

Atomic by construction

One writer, one transaction. Two processes cannot both observe the same headroom, and a refusal creates no attempt row.

Two horizons, one gate

Per-request ceilings, a daily cap, and a monthly cap. The dashboard names the cap that is currently refusing traffic.

Classified fallback

Connection errors, timeouts, 408, 429, and 5xx can move to the next target. Malformed bodies and other 4xx do not.

Redaction by default

Secret-shaped strings never reach the log. Redacting prompts before forwarding is opt-in, because it changes what the model sees.

Evidence, not a guess

SQLite ledger, per-request trace, Prometheus metrics, and CSV or JSON exports. Costs are estimates; the arithmetic is auditable.

A local operator console

Budget meter, request ledger, routing simulator, and read-only policy. Served by the gateway itself: no build step, no second service.

Tradeoffs, stated

Deliberately boring infrastructure.

The safety property should be easy to audit. There is no queue, no cache, no sidecar, and no build pipeline between the budget check and the provider call.

Read the architecture decisions →

  • One process, one writer. Budget correctness rests on SQLite's BEGIN IMMEDIATE, not on coordination between services.
  • No network by default. The shipped config terminates at deterministic fake providers, so the whole path is testable offline.
  • No prompt storage. The ledger keeps identifiers, tokens, cost, and outcome. Message content is never written.
  • No silent streaming. stream: true is a documented 400, not a request that quietly buffers.
  • No hidden spend. Rejected requests create no attempt rows, and settled spend can never exceed the reservation.

Quickstart

Run it locally.

Python 3.12. No provider credentials, no network, no spend. The dashboard is served by the same process.

Connect at http://127.0.0.1:8787/dashboard/ with the demo key demo-key-alpha, then watch the first two requests fall back from fake-primary to fake-backup. 

# Windows: .venv\Scripts\python
python -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
.venv/bin/python -m cost_firewall.cli serve --config config.example.toml

# health, models, and one completion
curl -s http://127.0.0.1:8787/healthz
curl -s -H "Authorization: Bearer demo-key-alpha" \
  http://127.0.0.1:8787/v1/models

What it will not do

Limits are part of the contract.

Estimates, not invoices
Costs come from a configured price table and provider-reported token counts. Reconcile against your provider's billing.
One database file
SQLite is the source of truth. The budget gate assumes one writer per deployment, not a shared cluster.
Process-local limits
Rate and concurrency caps are enforced per process; the budget transaction is the cross-process invariant.
Chat completions only
Non-streaming POST /v1/chat/completions. No tool-call retries and no side-effecting requests.
